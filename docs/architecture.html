Architecture Reference

Factory Inventory Management System

A two-process demo application: a Vue 3 single-page app talking to a Python FastAPI service over plain HTTP JSON. There is no database — seed data is loaded from JSON files into Python lists at import time and filtered in memory. One endpoint writes: submitted restock orders accumulate in a module-level list for the life of the process.

Because the JSON files are read at import time into module-level Python lists, the seed data is read-only for the life of the process. Editing a JSON file requires a server restart. Data Flow

What happens when a user changes a filter in the global filter bar:

  1. User changes a select in FilterBar.vue
    The v-model writes to a ref owned by the useFilters composable — not to local component state.
  2. Shared singleton state updates
    useFilters.js declares its four refs at module scope, outside the exported function. Every importer gets the same refs, so one filter bar drives every view without a store library or prop drilling.
  3. The active view's watcher fires
    Each view runs watch([selectedPeriod, selectedLocation, selectedCategory, selectedStatus], loadData), so a filter change re-triggers its fetch.
  4. Requests go out in parallel
    getCurrentFilters() maps UI state to API params (selectedLocation → warehouse, selectedPeriod → month). Views batch calls with Promise.all — the Dashboard issues four at once.
  5. api.js builds the query string
    Any value equal to 'all' is dropped rather than sent, so "no filter" is expressed by omitting the param.
  6. FastAPI filters in memory
    apply_filters() chains list comprehensions over the module-level lists (case-insensitive on category and status). filter_by_month() additionally accepts quarter keys like Q1-2025 via QUARTER_MAP. Filtering never mutates the source lists.
  7. Pydantic serializes the response
    Endpoints declaring response_model validate and shape the output. The analytics endpoints return plain dicts with no model.
  8. Raw data lands in refs; derived data is computed
    Views store responses in refs (allOrders, inventoryItems, summary) and express every rollup — status breakdowns, chart geometry, badge levels — as computed properties that recalculate automatically.

Three deliberate exceptions

  • Inventory has no time dimension. /api/inventory accepts only warehouse and category; the Time Period filter is silently ignored, because inventory records carry no order_date.
  • Some views bypass the filter bar entirely. /api/demand, /api/backlog, /api/spending/* and /api/reports/* take no filter params. Where filtering is still wanted, the frontend does it client-side — the Dashboard, for example, fetches all backlog items and then narrows them to SKUs present in the already-filtered inventory response.
  • Restocking ignores the filter bar entirely. The Restocking view does not consume useFilters at all: recommendations are driven by the budget slider and are warehouse-agnostic, and submitted restock orders have no customer, status or month dimension to filter on. The Orders tab's Submitted Orders section is likewise excluded from the filter watch that drives the customer-orders table beside it.

The restocking pipeline

Restocking runs on a different path from the filter-driven views, so it is worth reading separately.

  1. The slider sets a budget
    Its maximum is the cost of buying every candidate, learned from a probe request at budget=0. Refetches are debounced and the previous results stay rendered while one is in flight, so dragging does not flicker.
  2. The backend joins forecasts to inventory
    A forecast SKU with no inventory record has no unit cost and is skipped rather than guessed at.
  3. Quantity is an order-up-to target
    forecasted_demand + reorder_point − quantity_on_hand. Sizing on the raw demand gap instead yields one- and two-unit orders for the stable-trend items, which is not a meaningful purchase.
  4. Ranking is separate from sizing
    Items score on demand pressure (forecasted − current), boosted 50% when stock has already fallen to or below the reorder point, so urgent items outrank large-but-calm top-ups.
  5. The budget fill is greedy but does not stop early
    A line that overruns the remaining budget is skipped and cheaper lines further down the ranking are still considered, so one expensive item cannot strand the rest of the budget. Every candidate is returned flagged within_budget, so the UI can show what was left out.
  6. Submission re-prices server-side
    The client sends only SKUs and quantities; unit prices, names and warehouses are resolved from inventory, so a stale basket cannot set its own totals. Lead time comes from a per-category map and the order takes its slowest line.

Cross-cutting composables

  • useFilters — the four global filters, held as module-scope refs so all consumers share one instance. This is the app's entire state-management story; there is no Pinia or Vuex.
  • useI18n — hand-rolled EN/JA translation with dotted key lookup, English fallback, and localStorage persistence. Also translates data values (product, customer, and warehouse names), not just chrome.
  • useAuth — mock only. isAuthenticated is hardcoded true, the user object is a literal, and logout() raises an alert(). No tokens, no login route, no route guards.

Locale-driven currency

Currency is derived from locale rather than chosen independently: en implies USD and ja implies JPY. utils/currency.js converts with a hardcoded USD_TO_JPY = 150 constant — a display-time conversion, not a rate lookup.

Observations

Things found while tracing the code that are worth knowing before working in it. These are descriptions of the current state, not recommendations.

These are tracked in docs/KNOWN-ISSUES.md as BUG-001–BUG-008 and OBS-001–OBS-003, with file/line references, reproduce steps, and the open decisions for each. Titles below match the tracker entries. Add new findings there, not here.

BUG-005 is fixed — the 8 orphaned demand-forecast SKUs now have inventory records. tests/backend/test_data_integrity.py guards that class of break and surfaced three more (BUG-006 to BUG-008), pinned there as strict xfails.
The Tasks feature calls endpoints that do not exist Broken

api.js defines getTasks, createTask, deleteTask and toggleTask against /api/tasks, and App.vue calls loadTasks() on mount. The backend has no /api/tasks route — it returns 404 (verified against the running server).

The failure is invisible in the UI: every call is wrapped in try/catch that only does console.error, and the tasks list falls back to the four hardcoded mock tasks in useAuth.js. So the Tasks modal looks functional, but added tasks live only in browser memory and vanish on reload.

Purchase orders are half-built across all three layers Broken

The backend defines PurchaseOrder and CreatePurchaseOrderRequest Pydantic models and reads purchase_orders.json to compute the has_purchase_order flag on /api/backlog — but exposes no purchase-order routes. /api/purchase-orders returns 404, while api.js ships createPurchaseOrder() and getPurchaseOrderByBacklogItem() pointing at it.

Dashboard.vue renders <PurchaseOrderModal> in its template and maintains showPOModal state, but that component file does not exist in components/ and is not imported or registered — Vue will fail to resolve it at runtime and render nothing. purchase_orders.json is an empty list, so has_purchase_order is always false.

Backlog.vue is orphaned Dead code

views/Backlog.vue is a complete, working view — priority tiles, a backlog table, filter integration — but it has no route in main.js, no nav link in App.vue, and no import anywhere. It is unreachable. Backlog data does still surface on the Dashboard through a separate inline implementation.

Test documentation overstates the suite Doc drift

tests/TEST_SUMMARY.md claims 55 passing tests and itemizes suites including a 15-test Orders group. The actual run is 40 passed, from three files (test_dashboard.py, test_inventory.py, test_misc_endpoints.py) — there is no dedicated orders test file. All 40 pass; the count and breakdown in the doc are simply stale.

Reports.vue bypasses the API client Inconsistency

Every other view imports api from api.js. Reports.vue imports axios directly and hardcodes http://localhost:8001 twice in its own fetch logic, so the reports endpoints are the only ones absent from the central client.

Some dashboard figures are hardcoded, not derived Demo data

Dashboard.vue holds literals such as ordersData = { fulfilled: 187, goal: 200 } and fillRate = 96.8, and the revenue goal is a fixed $800K/month ($9.6M for a full year). These do not respond to filters the way the computed metrics beside them do.

No production hardening — by design Scope

CORS is allow_origins=["*"] alongside allow_credentials=True, there is no authentication or authorization, no rate limiting, no pagination on the 250-order endpoint, and the API base URL is hardcoded rather than environment-driven. The README states the demo scope explicitly; this is listed for orientation, not as a defect.
